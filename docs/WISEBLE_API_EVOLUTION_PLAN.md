## 2. 同步调用约定

同步调用让业务在一个后台任务中顺序执行；CoreBluetooth 仍通过库内部串行队列上的异步事件推进操作。这两者可以同时成立。

- 所有 `synchronized*` 和 `sendReceive:*` 方法只能在后台线程调用，不能在主线程或库自己的蓝牙回调队列中等待。
- 每一步取得成功结果后，业务再执行下一步；失败、超时或取消后，业务决定退出或如何处理。
- 库内部建立和结束等待，不依赖 App 的代理回调唤醒等待，也不依赖主线程处理结果来解除阻塞。
- 界面更新回到主线程，页面仍需判断自身是否有效；库不控制导航。
- 同步操作只有一个最终结果；超时或取消后到达的底层事件不能使它再次成功。

设计时约定的业务形态如下，为流程伪代码；对应同步接口已在 1.4.0 实现，App 接入结果见第 10 节：

```text
在一个后台任务中：
    连接设备，失败则退出
    开启配置通知，失败则退出
    发送 xxx 并等待响应，确认是 yyy 后继续
    发送 xxx2 并等待响应，确认是 yyy2 后继续
    开启数据通知，失败则退出
    回到主线程，确认页面仍有效后更新界面
```

## 4. 第一批：统一连接生命周期

### 4.1 连接入口与归属

- 保留并完善同步连接方式，明确成功是否已包含服务和特征发现，与现有行为保持兼容。
- 连接成功不代表业务初始化完成；订阅特征和流控查询仍由 App 顺序执行。
- 库内部管理连接尝试、取消、清理和有效性，不要求页面维护底层重试时序。
- 旧页面退出时的断开请求只能作用于它拥有的那次连接，不能仅按设备标识断开同一设备的新连接。
- 实施前明确取消和断开的归属表达方式，保留必要的调用归属信息；不能为了删除 App 的 UUID 参数而丢失旧页面隔离能力。
- App 仍决定何时取消、断开和进入下一页面。页面释放不作为隐式断开规则。

### 4.2 重试、取消与清理

- 同一设备同时只允许一个有效连接流程，不同设备的状态独立。
- 仅对适合重试的连接阶段错误执行有限重试；参数错误、权限不足、蓝牙关闭和用户取消直接失败。
- 连接与服务发现的超时范围、最大尝试次数及清理时间需有明确文档，避免一次调用无限等待。
- 重试前先结束上一次尝试。CoreBluetooth 回调不携带尝试编号，不能仅靠内部编号判断旧回调已安全隔离。
- 取消后停止后续重试，并及时结束相关同步等待；操作返回不等于底层清理已经结束。
- 已确认结束的连接再次断开，不新建等待记录；断开中的重复请求共享一次底层清理，各自只结算一次。
- 清理超时给出明确错误，没有终止证据时不擅自解除隔离或启动重叠连接。
- 覆盖 `didDisconnect`、`didFailToConnect`、蓝牙关闭及重置等终止路径，避免只等某一种回调而永久卡住。

### 4.3 同步结果与错误

优先采用调用级结果和可选错误输出，让业务在同步方法返回后就能判断原因，避免依赖共享的最后一次错误或额外代理回调。

错误至少区分：参数无效、调用线程不支持、未授权、蓝牙不可用、未连接、设备忙、连接失败、超时、用户取消、清理尚未完成、服务 / 特征不存在及操作不支持。保留可用的底层 `NSError`，App 按错误码映射中文提示。

新错误能力不改变旧方法的结果约定；库不输出 Toast，不要求业务通过中文字符串判断错误。

## 5. 第二批：完善同步发送与等待管理

### 5.1 同步只发送

在库中提供明确等待发送完成的同步入口，复用现有写入上下文、分包和背压处理。

- 参数包含设备、特征、数据、写入类型及超时，必要配置在提交时取快照。
- 在开始写入前建立本次等待，防止快速完成时丢失结果。
- 库内部直接结束等待，不通过主线程代理转发来唤醒同步调用。
- 参数无效、忙、超时、取消、断开或发送失败，均返回本次操作的明确结果。
- 无法区分旧回调时保留必要隔离，不简单删除上下文后立即接受冲突重试。
- 首版沿用冲突操作返回“忙”的规则，不为顺序调用额外引入任务编排器。

### 5.2 明确发送完成含义

- With Response：全部分包取得 GATT 写入确认后返回成功。
- Without Response：全部分包交给 CoreBluetooth 后返回成功，不代表硬件已经处理。
- 需要确认板子业务执行结果时，使用发送并接收，再由业务校验响应。
- 遵守对应写入类型的实际最大长度和系统背压，允许调用者设置更小的分包上限。
- 连接相关配置或本次调用参数不能因其他设备改写共享默认值而在执行中改变。
- 超时、取消或失败不等于设备未执行，不自动重发业务数据。

### 5.3 断开与取消唤醒

断开、蓝牙关闭或重置时，及时结束相关连接的同步连接、通知、读取、发送及响应等待。支持按操作或连接范围取消，避免全局取消误伤其他设备；具体入口以实际需要确定。

库保证等待及时返回并拦截失效连接上的操作，App 在失败后退出当前业务步骤。库不接管业务的循环、测试间隔和停止条件。

完成后，App 删除 `_sendEvent`、发送代理中的等待结算及页面侧 `synchronizedSendData` 包装。吞吐测试保留后台循环，按“同步发送成功 → 等待业务间隔 → 下一次发送”执行。

## 6. 第三批：完善同步发送并接收

保留 `sendReceive` 的同步使用方式。第一阶段补充本次调用可明确指定的发送特征、写入类型、响应特征、超时及错误结果，减少对共享 `commonResponeNotifyCharacteristic` 的改写。

必须保持和验证的规则：

- 写入前登记响应等待，避免快速响应丢失。
- 同一设备先保持一次只有一个请求等待响应，冲突返回“忙”。
- 响应按设备、有效连接及指定特征归属，断开和取消结束本次等待。
- 超时后的旧事件不能完成已结束操作；没有协议标识时，不能保证识别任意迟到响应。
- 明确普通数据监听与响应等待的分发规则，不悄悄吞掉 App 仍需处理的数据。

“收到 yyy 才执行下一步”可以先由 App 在同步方法返回后校验，不要求新增协议框架。如果实际设备存在主动上报混入或一条响应分成多个通知，再单独确定是否增加可选匹配、完整响应判断能力：

- 匹配及结束条件由业务提供，不硬编码板子指令。
- 一次 BLE 通知不一定是完整业务消息，库不猜测消息格式。
- 无请求编号且响应相同的协议，单靠连接标识无法辨认同一连接内任意迟到包，需要协议或业务约束。

这些协议扩展按实际需求另行确定，不作为前两批迁移的前提。

App 的初始化仍保持：识别特征能力 → 同步订阅配置通知 → 同步查询并解释流控 → 同步订阅数据通知 → 主线程确认页面有效后进入发送页面。

## 7. 事件、兼容与代码组织

- 扫描结果、主动上报和意外断开继续使用事件回调；每个事件明确设备及连接归属。
- 同步操作的内部完成不依赖页面是否设置代理，库也不通过占用公共 `connectDelegate` 实现内部管理。
- 页面监听的注册与移除规则在迁移时明确，旧监听不能误收新连接的数据；不预先建设通用事件框架。
- 保留 `connect:`、`synchronizedConnect:`、`send:`、`sendReceive:`、`disconnect:callBack:` 及已有代理接口的约定。
- 新旧入口共用同一套连接和操作状态，冲突经过统一检查，不能并行维护两套状态。
- 新接口使用正确拼写，已有 `loaclState`、`Nofity`、`Respone` 等保留兼容，不进行无关重命名。
- App 的测试替代接口不直接公开为库接口，硬件替代及回调时序构造留在内部测试中。
- 核对 umbrella header、podspec 和 Demo 工程引用，确保新增源码随库分发。
- 扫描列表去重、节流、排序和设备识别留在 App，不引入新的扫描列表框架。

## 10. App 接入记录（2026-10-21）

本批仅适配 wiseBle，不清理其他 Pod，不加入 SPM 或修改库端代码。

- App 和测试 target 统一通过 GitHub `https://github.com/diaoerlangdang/WiseBle.git` 的 `1.4.0` tag 引用库，对应提交 `1c7c46c`；已执行 `pod update wiseBle --no-repo-update`，其他 Pod 版本不变。
- 扫描页在一个后台任务中顺序执行同步连接、配置通知订阅、流控查询和数据通知订阅。每次新连接创建 UUID，成功后交给设备页，不再使用 App 协调器。
- 连接尝试参数保持每次 5 秒、最多 5 次、清理最多等待 2 秒，重试与连接状态由库管理。
- 取消或离开扫描页时使页面任务失效并按会话断开。对“后台任务即将登记，但取消先到”的窗口，仅在必要时补发取消，任务结束后自动停止，避免迟到任务继续连接或导航。
- 设备页直接调用带会话、分包上限和错误输出的 `synchronizedSend`，删除 `_sendEvent`、发送完成代理和页面同步包装；手动发送、自定义指令和测试循环使用页面串行发送队列。
- 发送参数在任务启动前固定，不再改写库的公共发送、响应特征或分包默认值。测试只统计成功发送的数据，失败即停止；停止测试取消当前会话的等待，测试标识阻止旧循环继续或覆盖新测试状态。
- 接收与断开监听改用 `WWBLEDidReceiveDataNotification` / `WWBLEConnectionDidDisconnectNotification`，按设备和会话严格过滤；缺失会话的事件不再接受。
- 删除重复的 `HJBleConnectionCoordinator` 及专属测试。连接生命周期回归由库覆盖，App 增补使用真实 Pod 的顺序初始化、分包、会话通知、断电重连及取消测试。

### 行为变化

声明支持配置服务的设备，流控查询失败或超时现在会结束初始化、清理连接并提示失败。此前 App 会按未启用流控继续进入设备页；1.4.0 会保留请求超时后的迟到回调隔离，不能在失败后继续使用该连接发送，否则可能持续返回忙。需在实机确认所用固件正常响应 `<RD_UART_FC>`；不支持配置特征的普通 BLE 设备仍直接订阅数据通知。

无响应写入成功表示分包全部交给系统，不代表板子已经处理。真实吞吐、系统背压和协议响应仍需硬件验收。

### 实机验收参考

2026-10-22：用户反馈本次适配测试无问题，iOS App 版本号更新为 `4.4.1`。以下保留回归场景供后续版本参考；用户未逐项报告结果，不将其记录为逐项完成。

1. 正常扫描连接，核对流控显示、手动文本 / HEX、CRLF、自定义指令及有 / 无响应两种写入。
2. 进入设置页再返回、打开 / 关闭自定义指令页面，连接继续有效；正常返回及完成侧滑退出后可再次连接，取消侧滑保持连接。
